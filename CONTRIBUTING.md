# Contributing

Thanks for your interest. This repository is a specification and its executable conformance corpus,
so contributing here is a slightly unusual activity: **nothing in the corpus except a reject vector
is hand-edited** — round-trip documents are generated by the resident emitter and behavioural
scenarios by a conformant host — and the normative text and the corpus move together or not at all.

## Developer Certificate of Origin

Contributions are accepted under the [Developer Certificate of Origin](https://developercertificate.org/).
Sign off each commit with `git commit -s`, which appends a `Signed-off-by:` trailer.

## The forward-coupling rule

A change to any specified member, ordering, encoding, refusal class or derived value updates **five
artefacts in the same change-set**:

1. the normative text in [`PROGRAM_WIRE.md`](PROGRAM_WIRE.md),
2. the schemas in [`schemas/`](schemas/),
3. **all three** emitters — the resident [`wire-fixtures/emit.mjs`](wire-fixtures/emit.mjs), which
   mints the bytes; [`wire-fixtures/emit-independent.mjs`](wire-fixtures/emit-independent.mjs); and
   [`wire-fixtures/emit-ordinal.py`](wire-fixtures/emit-ordinal.py), which derives the same documents
   in a language whose native string comparison is not §2 rule 3's ordering. Each was written from
   the normative text alone and must be brought to the same answer *by that text* rather than by
   reading another — or, for the
   driver-semantics family, [`wire-fixtures/check-scenarios.mjs`](wire-fixtures/check-scenarios.mjs),
   which checks a trace's shape rather than reproducing its content, for the reason §11.1 gives,
4. the vectors, scenarios and digests in [`wire-fixtures/manifest.json`](wire-fixtures/manifest.json),
5. **the codec of every host that certifies against this corpus** — and, where the change touches
   §6's loop or §10.3's format, that host's driver harness too.

This is §11.1 of the specification. The fifth is the one that is easy to leave out and the one that
makes the other four mean something: a corpus the hosts have not caught up with is a specification of
nothing, and nothing in this repository will say so. A change that cannot land the host side in the
same change-set is a change that is not ready — say so in the issue rather than landing four fifths of
it.

The corpus lives in one repository and the hosts live in others, so "the same change-set" spans
repositories by construction. Land them together, and **push them together**: a corpus regen left
unpushed is invisible to every host and to every gate that reads it.

Run the gate before you open a pull request:

```
pwsh ./run.ps1
```

It reproduces every round-trip document from **each** emitter and compares byte for byte against
what is committed, compares the three emitters against **each other**, re-derives every handler
vector's declared `replaySafety` and `replayReasons` twice over, checks the manifest's
structural invariants — every enumerated vector and scenario present, every present file enumerated,
every digest matching its file, every refusal class drawn from Appendix A, every arm of both
closed effect vocabularies covered, and every document-reachable arm of §7.5's replay-defect
vocabulary discriminated by a vector carrying that token and no other — checks that every
driver-semantics scenario still has the shape
§10.3 gives it, and then proves each checker can go red **for the perturbation it was handed**
against a scratch copy.

## Five things that are easy to get wrong

**Do not settle a disagreement between the emitters inside an emitter.** The corpus carries three,
written from the normative text separately and never from one another, and
`wire-fixtures/compare-emitters.mjs` runs them against each other in the gate. Agreement there is
**unanimity, never a majority**: two of the three are JavaScript, so a two-against-one split is
most likely evidence about what that runtime supplies for free rather than about which reading is
right. When it goes red, the
first question is whether the specification determines those bytes at all — because a rule the text
leaves open is one a *single* emitter can never fail: it closes the rule its own way, and the
fixtures it mints then pin that choice as though the text had made it. Where the text does decide,
one emitter has a defect and the text says which. Where it does not, the defect is in the **text**,
and the fix is the five-artefact change-set above starting with the sentence that failed to decide.
Editing whichever emitter looks wrong converts a specification defect into a convention two files
share, silently, and takes the detector out with it.

**Do not hand-edit a round-trip fixture.** A fixture file's bytes *are* the wire document — no
trailing newline, no wrapper — and the manifest records a digest of the file itself. Editing one by
hand and updating its digest to match produces a corpus that is internally consistent and no longer
describes what any emitter emits. Change the model in the emitter, then
`node wire-fixtures/emit.mjs --write`.

**Do not add a `reject` vector to the resident emitter.** Reject vectors are documents a conformant
reader must refuse; they are hand-authored on purpose, because reproducing their bytes would
demonstrate nothing about the refusal. Every reject vector names a class from Appendix A — a refusal
for some other reason is not a pass, since it would let a reader certify by being broken in a
convenient way.

**Do not "fix" the client-effect envelope.** §5.2 is the specification's one enumerated exception: a
`kind` discriminator and declaration-ordered members, because those bytes are a shipped wire a
rendering surface already reads. Encoding that family with the ordinal encoder would silently erase
the exception the corpus exists to pin — which is why `emit.mjs` keeps two encoders rather than one
with a flag. Unifying it is a migration with a version bump, not a tidy-up.

The exception reaches further than that family's own vectors, and this is where it is easiest to
erase by accident: a driver-semantics step records each effect it emitted as a **string** whose
contents are that document's own bytes. It is not embedded as an object, because a JSON writer would
then be free to re-order its members Ordinally — the "correction" above, applied in the one place
nobody reviews. `check-scenarios.mjs` checks the member ORDER of every recorded effect for exactly
that reason, and the gate's self-tests include the re-ordering as a perturbation.

**A recorded denial is the OPPOSITE case, and treating it like an effect is the mistake here.** §5.3's
shape is one this specification owns outright — canonical, no exception — so a step's `denials` are
embedded as *objects*, and a host certifies by reading them into its own denial vocabulary rather than
by diffing bytes. Two rules about them are ones no schema can state and the checker therefore does:
`origin` may sit only on `GateRefused`, because an `Unregistered` denial consulted no destination; and
`origin` is an **origin** — a host, or the class of destination where there is no host. A denial that
quoted a path or a query would have put the payload of a refused exfiltration attempt into the audit
trail that refusing it kept out, which is the one perturbation in the gate that is a security defect
rather than a shape defect.

And the member that makes a denial reproducible at all lives in the manifest rather than in the three
files: a scenario recording denials names a **`hostPolicy`**, and every host constructs what that name
denotes. Do not put a policy in a fixture as data — a corpus that carried one would be specifying it —
and do not let a host fall back to its own default on a name it does not recognise, which would report
a scenario nobody evaluated as one that passed. Registering a new name is a five-artefact change like
any other, and it enumerates rather than renumbers.

**Do not hand-edit a scenario, and do not add one to the manifest with a script.** A scenario's trace
is what a bounded loop *did*; the only thing that can write one is a bounded loop, and a host's emit
path must refuse to record a trace while its own placements disagree. Add the scenario to a host's
seed set, regenerate, add the manifest entry **by hand**, then `node wire-fixtures/check-scenarios.mjs
--write` to refresh the digests and step counts. That tool deliberately refreshes only entries that
already exist: a host able to add itself to the index it is certified against would be grading its own
paper. [`wire-fixtures/README.md`](wire-fixtures/README.md) has the sequence in full.

## Proposing a change to the normative text

Open an issue first. A specification change is a change to every implementation that reads it, so the
useful question is not "should the format allow this" but "what does a conformant reader do with a
document that predates the change" — say what you expect that to be, and the discussion will be much
shorter.

Two kinds of proposal have a standing answer, so read §9.5 and §8.4 before writing one: giving a
program the ability to parameterise a handler, and offering exactly-once. Both were considered and
foreclosed with reasons, and a proposal that does not engage those reasons will get them back.
